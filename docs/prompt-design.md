# Prompt 设计：让课程规则可核对

这份设计回答一个问题：学生给出课程材料后，AI 应该整理出什么，才能生成一张可信的成绩表？AI 的职责是提取材料中的规则和成绩事实，计算与目标倒推交给程序，规则是否准确仍由学生核对。

**当前状态：**[提取 Prompt v0.1](../prompts/extract-rules.md) 与实验案例已准备，真实模型实验尚未执行。网页只用配套材料的固定结果演示“模拟提取”，没有调用这份 Prompt，也没有模型输出自动导入接口。

## 1. 从一个容易算错的场景出发

学生的材料可能分在几处：课程说明列考核占比，作业页写原始满分，另一则通知写期末最低分要求。只提取其中一张表，即使加权公式正确，也可能漏掉影响通过的条件。

以人工构造的材料片段为例：

```text
M1：课程论文占总评 40%。
M2：论文满分 30 分，已公布成绩为 24 分。
M3：我希望总评达到 75 分。
```

提取时要分开记录：占比是 40%，满分是 30，实际成绩是 24，个人目标是 75。不能把占比当满分，也不能把个人目标当成学校及格线。材料没写通过线和额外要求，就列出缺失问题，不能默认“50 分及格、没有其他条件”。

因此只设计一类提取 Prompt：**把一门课的一组材料变成候选规则与具体问题。**本轮不加入成绩预测、学习建议或聊天问答任务。

## 2. 输入、输出和责任分工

| 环节 | 负责什么 | 不应代替什么 |
| --- | --- | --- |
| 输入材料 | 截图、文字、补充说明分别编号；学生提供的实际／预计成绩也注明来源 | 不把人工标准答案一并交给模型 |
| AI 提取 | 整理规则、成绩事实、原文依据和缺失／冲突问题 | 不补猜规则，不计算最终分数，不替用户确认 |
| 学生核对 | 对照原材料确认项目、占比、满分、及格条件和成绩性质；有误时修正 | 不要求从空表重新抄写整门课 |
| 程序校验与计算 | 检查受支持的规则及输入范围，再计算目标要求 | 校验通过不能证明提取与原材料一致 |

完整模板保留在 [prompts/extract-rules.md](../prompts/extract-rules.md)，本文件解释设计理由，不复制整份 Prompt。模板按“角色与任务 → 处理原则 → 输出结构 → 编号材料”组织；材料里夹带的任务指令只作为数据处理。

## 3. 为什么需要固定字段

固定字段让“这是什么数字”有明确答案，便于成绩表展示和逐项核对。字段填全只表示结构齐全，不表示内容正确。

| 需要回答的问题 | 候选字段 | 设计理由 |
| --- | --- | --- |
| 哪一项考核，怎么算分？ | `items` 中的 `id`、`name`、`weight`、`max`、`step` | 分开项目、占比、满分和给分单位；不知道步长时不默认整数分 |
| 是已经拿到的分数，还是假设？ | `actual`、`expected` | 预计只记录学生给的假设，不能由 AI 预测或改写为实际 |
| 想拿多少，与及格有什么区别？ | `targets`、`passMark` | 个人目标和学校通过线分别核对，不根据 P／D 标签猜阈值 |
| 是否还有单项最低要求？ | `hurdleStatus`、`hurdles`、`hurdleCombination` | 保留对应项目、比较符号、阈值、单位及条件关系 |
| 这个值从哪里来，有什么疑问？ | `evidence`、`conflicts`、`issues`、`questions` | 让用户核对具体字段和原文，不只看到笼统的“请检查” |
| 当前计算器能处理吗？ | `unsupportedRules`、`ruleStatus` | 不支持的规则保留原文，不删掉后继续给出结论 |

数值统一为十进制字符串或 `null`：20% 占比写为 `"0.2"`，明确零分写为 `"0"`，没出分写为 `null`。各非空材料事实需要来源引用；项目 ID 等结构字段不要求原文依据。

如果上例只有 M1，论文条目应是下面这样。这是**人工构造的格式片段，不是模型实测输出**：

```json
{
  "id": "essay",
  "name": "课程论文",
  "weight": "0.4",
  "max": null,
  "actual": null,
  "expected": null,
  "step": null
}
```

完整候选还应在 `evidence` 中引用 M1 的占比原文，在 `issues` 和 `questions` 中指出“论文原始满分是多少”。收到 M2 后可以补充满分和实际成绩，仍须由学生核对。

## 4. 信息有问题时如何处理

| 材料中的情况 | Prompt 要求的候选结果 | 用户需要核对什么 |
| --- | --- | --- |
| 有占比，没有原始满分 | 满分留空，提出具体问题 | 找到该项满分，不能默认 100 |
| 没读到额外及格要求 | `hurdleStatus: "unknown"` | 确认材料是否完整；“没读到”不等于“没有” |
| 原文明确没有额外要求 | `none_in_source` | 原文是否确实覆盖全部通过条件 |
| 图中期末最低 40%，补充文字为 50% | 争议值留空，两个候选及来源都放入 `conflicts` | 确认哪条有效；不按材料顺序自动覆盖 |
| 期末必须严格大于 50% | 保留 `>` 和原文，标为 `unsupported` | 当前仅支持 `>=`，不能悄悄改写 |
| 去掉最低一次测验、补考替代或复杂 OR 条件 | 放入 `unsupportedRules`，暂停正式计算 | 当前版本无法完整表达这类规则 |
| 同一项同时有实际和预计成绩 | 分别保留输入，标记旧预计已失效 | 哪个是老师公布的分数；不能相加 |
| 输出了来源中没有的值或引用 | 实验中计为错误 | 有 JSON 和引用字段仍不代表有依据 |

这些约束已经写进 Prompt，**是否有效还需真实模型实验验证**。它们不会让当前网页自动识别新材料中的冲突或特殊规则。计算支持范围见 [计算契约](calculation-spec.md)。

## 5. 为什么生成成绩表后还要核对

模型输出是候选结果。即使格式正确、占比合计 100%，仍可能把作业满分或期末最低要求读错。核对放在生成之后，让学生修正已有内容，同时保留正式计算前的确认动作。

候选只允许 `pending`（待核对）或 `unsupported`（暂不支持），不能输出 `confirmed`（已确认）。来源里的 `none_in_source` 也不等于学生已经确认没有额外要求。

当前网页的成绩表、修正和确认流程已经实现；它使用的是配套样例数据。未来若接入模型，还需要候选格式校验和字段转换。例如实验候选的未知值是 `null`，网页课程记录使用空字符串；候选来源列表也不同于网页现有的来源说明字段。**不能把实验 JSON 直接当作已确认课程写入保存记录。**

模型可以提取学生材料中明确提供的实际成绩，但候选提取不能跳过核对、直接覆盖已保存的实际成绩。已有课程的成绩修改规则见 [状态设计](state-design.md)。

## 6. 如何判断这份 Prompt 有没有用

现有 5 个合成案例覆盖完整输入、缺失字段、来源冲突、严格大于、去掉最低成绩。输入、人工答案和执行说明在 [实验目录](../evaluation/README.md)。真实课程材料及真实模型输出尚待补充。

实验应固定 Prompt 版本和输入，保存首次完整输出，再核对四件事：关键字段对不对、额外条件有没有漏、冲突是否保留、引用能否支持该值。JSON 可解析单独记录，不代替内容正确。

发现错误后记录原输出、原因与修改，再用相同输入复测；追加提示后的答案与首次输出分开。详见 [评测说明](validation.md)。这能评价所测材料上的提取表现，不能证明网页已经接入模型，也不能用现有 93 项程序检查代替模型准确率。
