# 项目学习笔记：从六个设计取舍理解 AI 产品

更新：2026-11-25。记录课程成绩规划 Demo 中做过的选择、选择的理由，以及还没有验证的判断。需求和验收定义见 [产品需求](../docs/product-requirements.md)，完整设计过程见 [产品案例](../docs/product-case.md)。

## 1. 表单变短，不一定让任务变简单

初版让用户逐项手工填写课程；页面过长、术语难懂后，先把设置拆成三步。这个调整改善了信息排列，但用户仍要从材料中找出项目、占比和满分，再抄进表单。

发起人随后明确提出：应从材料直接生成成绩表。于是取消手工建课前置，把规则编辑移到生成之后。用户面对的是已有结果，可以核对并纠正，而不是从空白开始填写。

例如材料已写“作业 A 占 30%，满分 20”，生成后应让用户检查这两个值。若仍要求先填课程名称、逐项添加作业，省去整理的核心任务就没有解决。

**这次学到：先问用户少做了什么，再判断页面是否变简单。** 当前样例已能演示这个流程，但真实材料提取未接入，也没有同学耗时对照；因此只能说改变了任务路径，不能说已证明更省时。

对应证据：[导入改版记录](../docs/verification-import-demo-2026-11-25.md)、[当前产品流程](../docs/product-requirements.md)。

## 2. 让 AI 整理材料，把确定的计算交给程序

课程材料需要先变成可使用的字段。以“期末占 50%”为例，它只说明期末在总评中的占比，不能推出期末满分是 100，也不能推出期末最低需要 50 分。

因此 [提取 Prompt](../prompts/extract-rules.md)把权重、原始满分、实际／预计成绩、额外及格要求和来源分开。材料没写就留空；两份材料互相矛盾就保留冲突；首版不能计算的规则保留原文并标记。学生核对规则后，程序再按固定公式算分。

“结构化输出”在这里就是把一段材料拆成能显示、保存和逐项检查的数据。JSON 格式正确只说明程序读得进去；如果把权重写成满分，仍会产生错误结论。

**这次学到：字段设计要同时服务页面、计算和核对。** 生成结果可修正，既减少从头录入，也给错误留出纠正入口。代价是用户仍需核对关键规则，不能把出现一张表当成规则已可信。

当前完成了字段约定、Prompt 和合成案例；网页使用固定样例模拟提取。真实模型能否按这些要求输出仍待实验，见 [实验说明](../evaluation/README.md)。

## 3. 同一个数字，放在“实际”和“预计”里含义不同

作业 B 满分 40、占总评 20%。预计拿 30 分时，它在试算中贡献 15 分；实际公布 32 分后，实际贡献变为 16 分。两者不能相加，预计贡献也不能算进“已经拿到的分数”。

因此保留两种视角：只看实际成绩时，计算所有剩余考核的整体要求；填写预计成绩后，计算这些假设下的剩余要求。只有一项未知时才倒推该项具体分数，多项未知时不编出唯一组合。

实际成绩确认后替代本项假设并清空本项旧预计，其他项目保留。空白表示未知，实际 0 分表示已经出分；清空实际成绩后回到未知，不能偷偷恢复旧假设。

**这次学到：数据状态本身就是产品含义。** “按预计可以达到目标”和“实际已经达到目标”必须分开呈现，否则数字即使算对，用户也可能理解错。

对应证据：[计算契约](../docs/calculation-spec.md)、[B 预计 30 与实际 32 的浏览器记录](../docs/verification-browser-2026-11-25.md)。用户能否理解两种视角仍需任务观察。

## 4. 已出成绩要保护，也要允许纠正

实际成绩公布后会被后续计算反复使用，误改一次就会影响剩余要求。但完全禁止修改也不合理：录入可能出错，老师也可能调整成绩。

当前设计是默认锁定，显式进入修改，在草稿中填新值，核对原值与新值后才确认。取消时保留原记录。预计成绩用于尝试不同情况，可以直接调整，减少反复试算的操作成本。

例如 B 实际为 32，输入 31 后取消，成绩仍应为 32；只有最终确认后才改变。这个保护多了一次核对动作，是否清楚且不过度打断，仍需观察同学操作。

**这次学到：确认步骤应放在改变重要事实的位置。** 不必让每次假设试算都重复确认，也不能让重要记录随输入立即改变。

对应证据：[状态设计](../docs/state-design.md)、[确认、取消与刷新记录](../docs/verification-browser-2026-11-25.md)。

## 5. “页面变了”和“保存成功”是两件事

持续使用需要明确三种数据：正在编辑的草稿、用户已接受的记录、浏览器已经保存的记录。保存失败时，页面内的新值可以保留，但必须说明尚未保存；刷新后能恢复什么取决于最后成功写入的记录。

开发检查实际发现过一个问题：保存失败后进入规则草稿，再点击“重试保存”，可能提前保存尚未确认的改名。修复后，重试只保存已接受的课程；规则草稿要等用户正式保存才生效。

这个问题说明，按钮叫“重试”还不够，必须明确重试的是哪份数据。多标签页出现更新时也需要暂停覆盖，避免旧页面悄悄盖掉新记录。

**这次学到：连续使用的关键包括出错后保留什么、何时允许覆盖。** 当前选择同一浏览器本地保存，适合演示单课程的持续更新；代价是换浏览器或地址无法自动接续，原图不持久保存，也没有备份功能。

对应证据：[保存草稿问题与修复](../docs/verification-import-demo-2026-11-25.md)。保存异常的自动检查已覆盖部分逻辑，真实浏览器异常路径仍待补。

## 6. 每一种结论，都要有相应的验证

本项目已有 93 项自动检查通过，但这个数字回答不了“模型是否理解了材料”或“同学能否看懂页面”。把不同问题拆开，才知道下一步该补什么。

| 想说明的结论 | 需要的证据 | 当前情况 |
| --- | --- | --- |
| 已覆盖算例的结果符合规则 | 独立手算答案与程序比对 | 已有计算检查 |
| 修改、取消与刷新能正常工作 | 实际浏览器操作记录 | 部分本地路径已走查，完整验收待补 |
| 模型能准确提取规则 | 固定输入、首次模型输出、人工答案及逐字段比对 | 已备 Prompt 与 5 个合成案例，未运行 |
| 学生能完成二次更新、理解结果 | 同学任务观察及误解记录 | 未开始 |
| 公开 Demo 可访问且可操作 | 发布、资源访问及线上操作分别核验 | 已发布且 HTTP 可达，线上交互待验收 |

人工答案也要独立于程序。如果用同一段错误计算生成预期，再用它测试自己，就可能两边都错却显示通过。最低分遗漏、把预计当实际等影响结论的问题，需要逐例检查，不能被总体通过数掩盖。

**这次学到：作品集应说明证据支持到哪里。** 模拟流程可以帮助展示设计，不能证明模型质量；主界面截图能展示信息布局，不能独自证明刷新后数据仍在。

下一步最有价值的学习来自实际记录：补齐浏览器路径，观察同学在哪里误解，再用固定 Prompt 取得模型首次输出。验证方法与证据入口见 [验证设计](../docs/validation.md)。
